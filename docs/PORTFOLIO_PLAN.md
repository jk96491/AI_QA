## 1. 목표

- 작성자 배경: **게임 업계 RL 경력이 긴 사람**. 이 작업은 그 경험에서 나온 문제의식이다.
- 읽는 사람: 게임 회사 기술 리더·AI 팀·QA·기획. 코드를 읽지 않는 사람도 구조는 이해할 수 있게.
- 전할 것 한 줄: **"RL을 게임에서 떼어 냈다. 행동 구조(BT)는 필요한 쪽이 설계하고, RL은 그쪽이 지정한 가중치만 학습해 모델로 돌려준다."**
- 보여 줄 역량: 기존 게임 RL의 한계를 정확히 짚는 힘, 역할을 나누는 구조 설계, 그 구조가 실제로 게임을 바꿔 끼워도 도는지 검증한 것.

## 1-1. 핵심 주장 (문서 전체의 뼈대)

**문제: 기존 게임 RL은 환경·게임에 너무 묶여 있다.**
- 관측·행동 공간이 게임마다 달라 게임마다, 패치마다 처음부터 다시 만든다.
- 정책이 블랙박스라 기획자가 손댈 수 없고, 왜 그렇게 행동하는지 설명하기 어렵다.
- 학습 쪽이 게임 내부를 알아야 해서 게임 팀과 AI 팀이 따로 일할 수 없다.

**변화: LLM 덕분에 페르소나에 맞는 BT를 짜는 일은 쉬워졌다.** 남은 어려운 문제는 그 BT를 *잘* 움직이게 하는 수치(가중치)다. 사람이 손으로 맞추면 습관이 섞이고, 패치마다 다시 해야 한다.

**해법: 역할 분리.**

| 누가 | 하는 일 |
|---|---|
| 필요한 쪽 (게임 팀·기획, LLM 보조) | 페르소나별 BT 설계 + **"이 가중치를 이 범위에서 학습해라"** 선언 (정의서) |
| RL 플랫폼 (게임과 무관) | 선언된 가중치만 학습 (판 단위 최적화 / 상황별 정책) → **가중치·모델 제공** |
| 둘 사이 | 게임과 AI가 주고받는 약속(프로토콜) 하나뿐 |

- RL이 배우는 것이 "게임 전체를 조작하는 법"이 아니라 "주어진 BT의 손잡이 몇 개"라서, 학습 플랫폼은 게임이 바뀌어도 그대로다.
- 결과물이 BT + 가중치라 사람이 읽고 고칠 수 있다.
- LLM(구조를 짠다)과 RL(수치를 맞춘다)이 경쟁이 아니라 분업이 된다.

**검증: 이 프로토타입이 보여 주는 것.**
- 학습 플랫폼은 게임 데이터를 한 줄도 읽지 않는다. 학습할 가중치·범위는 게임이 정의서로 알려 준다.
- 같은 학습 플랫폼이 파이썬 대역 게임과 **다른 에이전트가 따로 만든 Unity 게임**에서 코드 수정 없이 돌았다.
- 밸런스 QA는 이 구조를 적용한 첫 사례다: 페르소나별로 최적화된 플레이로 수천 판을 돌려 수치로 답한다.

## 3. 핵심 일화 (구조의 쓸모를 보여 주는 장면)

0. **게임을 바꿔 끼움**: 파이썬 대역 게임 → 다른 에이전트가 만든 Unity 게임. RL 쪽 수정 없이 적합성 검사 통과 후 같은 사이클이 돌았다 (1-1장 주장의 직접 증거, 맨 앞에 둔다).

기술 설명 대신 **"이 구조라서 이런 걸 찾았다"** 는 장면으로 보여 준다.

1. **AI가 부활을 회복 수단으로 씀 (0.3.0)**: 학습 후 클리어율은 98%였지만 판마다 2~3번 죽었다. 사람 QA라면 놓쳤을 설계 허점을 수치로 찾았다 → 게임 쪽 부활 규칙 수정으로 이어짐.
2. **안정형 AI가 클리어를 포기함 (0.4.0)**: 학습할수록 클리어율이 0%로 떨어졌다. "안 죽고 시간 초과"가 보상상 더 이득이었기 때문. 원인을 게임 쪽(전사 생존력)과 보상 쪽(실패 벌점 없음)으로 나눴고, 보상을 고치자 클리어율이 92~96%로 돌아왔다 → **보상 설계가 곧 QA 기준을 정하는 일**이라는 점을 보여 줌.
3. **AI가 멈춰 버린 판 (0.2.0)**: 생존 행동에서 빠져나오지 못하는 판 3% → 프로토콜에 "멈춘 판" 개념 추가, 이후 0%.
4. (선택) 손 튜닝 대비 학습 결과: 마법사 손 튜닝 클리어 62% → 학습 후 90%. 기획자가 정한 기본값이 그 직업이 낼 수 있는 성능을 낮게 보여 준다는 원문 주장을 뒷받침.

## 5. 쓰는 원칙

- **뺄 것**: V-trace, Beta 분포, torch 버전, JSON 필드, 하이퍼파라미터, 테스트 개수. 필요하면 부록 한 줄 또는 저장소 링크로.
- **용어는 풀어 쓴다**: CMA-ES → "파라미터 자동 탐색", IMPALA → "상황별로 판단을 바꾸는 정책 학습", 프로토콜 → "게임과 AI가 주고받는 약속".
- 숫자는 장마다 1~2개만, 반드시 비교와 함께 (전/후, 손 튜닝/학습).
- 역할 구분을 분명히: 제안서 작성, 학습 플랫폼 설계(AI 도구와 협업), 게임은 별도 에이전트가 제작 → **여러 AI 에이전트를 나눠 맡긴 개발 방식**도 하나의 강점으로 짧게 소개.
- 한계는 숨기지 않는다: 테스트용 게임이고 결과는 경향. 이 솔직함이 신뢰를 준다.
